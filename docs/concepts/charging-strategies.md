# Charging strategies

A charging strategy decides **when** a vehicle draws its energy within its plug-in window. EPIOT
implements four strategies. Three are simple rule-based simulators that run locally in
`backend/aggregators.py`; the fourth delegates to the ReFlex optimisation service.

## Notation

| Symbol | Meaning |
|---|---|
| $P$ | Rated power of the charging point in kW; **11 kW** if unknown or ≤ 0 |
| $E$ | Energy demand of the session in kWh |
| $\Delta t$ | Step length, $\tfrac{1}{6}$ h |
| $s_a,\ s_d$ | Arrival and departure step (see {doc}`time-model`) |
| $n$ | Number of full-power steps needed |
| $p_t$ | Aggregated load at step $t$ (kW) |

Each simulator loops over the sessions, adds each one's contribution to three 288-step arrays —
load, upward flexibility and downward flexibility — and returns them. The aggregate of an area is the
sum over all its sessions.

```{mermaid}
flowchart TB

    C[(Rated power<br/>per charger)] --> L
    L --> M[Map arrival / departure<br/>to steps s_a, s_d]
    M --> N[Steps needed<br/>n = ⌊E / P·Δt⌋]
    N --> X{Strategy}
    X -->|afap| A[Block at s_a]
    X -->|alap| B[Block ending at s_d]
    X -->|avg| V[Half power from s_a]
    A & B & V --> AGG[Add to load,<br/>up-flex, down-flex arrays]
    AGG --> R[[288-step profiles]]
```

## As Fast As Possible (`afap`)

*Uncontrolled charging*: the vehicle charges at full power from the moment it arrives until its
energy demand is met or it leaves.

$$
n = \min\!\left(\left\lfloor \frac{E}{P\,\Delta t} \right\rfloor,\ s_d - s_a\right),
\qquad
p_t \mathrel{+}= P \quad \text{for } s_a \le t < s_a + n .
$$

If the window has room left, a partial step is added at $t = s_a + n$ for the remainder
$E \bmod P\Delta t$.

**Use it as** the business-as-usual baseline: it is how most public chargers behave today and it
produces the highest, earliest peaks.

## As Late As Possible (`alap`)

*Delayed charging*: the same full-power block, shifted so that it finishes at departure.

$$
n = \min\!\left(\left\lfloor \frac{E}{P\,\Delta t} \right\rfloor,\ s_d - s_a\right),
\qquad
p_t \mathrel{+}= P \quad \text{for } s_d - n < t \le s_d .
$$

A remainder step is added at $t = s_d - n$ when the window allows.

**Use it as** the opposite bound of the feasible region: together, `afap` and `alap` bracket every
schedule that charges at full power.

## Average Power (`avg`)

*Smoothed charging*: the vehicle charges at **half** its rated power from arrival.

$$
n = \min\!\left(\left\lfloor \frac{E}{\tfrac{P}{2}\,\Delta t} \right\rfloor,\ s_d - s_a\right),
\qquad
p_t \mathrel{+}= \tfrac{P}{2} \quad \text{for } s_a \le t < s_a + n .
$$

**Use it as** a simple proxy for power-limited smart charging. Halving the power doubles the
charging duration; when the plug-in window is too short, the energy delivered is capped by the
window (in the district comparison below, 2,396 kWh instead of 2,775 kWh).

## Min. Charging Cost (`ocost`)

*Price-optimal charging*: each vehicle's schedule minimises its energy cost against the day-ahead
electricity price, subject to delivering its energy within the plug-in window.

```{mermaid}

        V->>R: GET /services/run/info/{id}

    V->>R: GET /services/run/results/{id}
    R-->>V: devicePlans (energy per step, J)
    V->>V: J / 600 / 1000 to average kW, sum devices, derive flexibility
```

The query sent to ReFlex has this structure (one `evChargePoints` entry per charging point):

```json
{
  "runType": "singleRunConfig",
  "congestionPoints": [],
  "globalTarget": {
    "start": "2025-10-14T00:00:00Z",
    "timeStepDuration": "PT10M",
    "elements": [{ "targetType": "price", "value": 84.2 }, "… 288 elements …"]
  },
  "assets": {
    "evChargePoints": [
      {
        "id": "40405",
        "minChargePower": 0,
        "maxChargePower": 11000,
        "chargeSessions": [
          { "startTime": "2025-10-15T08:00:00Z", "endTime": "2025-10-15T17:00:00Z", "energyToCharge": 79200000 }
        ]
      }
    ],
    "nonFlexibleAssets": []
  }
}
```

Powers are in W and energies in J ($1\ \text{kWh} = 3.6\times10^{6}\ \text{J}$). See
{doc}`../related-tools/reflex` for the service itself.

:::{note}
`ocost` depends on two external services: Energy-Charts for prices and the ReFlex instance at
`drive2x-reflex.hesi.energy`, which is reachable only from the project network. The request blocks
while ReFlex is polled, with a 120-second polling deadline and 10-second individual request timeout by default. The shared instance can queue runs. See the ReFlex access and test instructions for endpoint configuration.
:::

## Comparing the strategies

| | `afap` | `alap` | `avg` | `ocost` |
|---|---|---|---|---|
| Power level | $P$ | $P$ | $P/2$ | 0 … $P$ (optimised) |
| Start of charging | Arrival | Departure − duration | Arrival | Optimised |
| Respects departure | Truncated at $s_d$ | Ends at $s_d$ | Truncated at $s_d$ | Constraint |
| Typical peak | Highest, early | High, late | Lower, early | Follows low prices |
| External calls | – | – | – | Energy-Charts, ReFlex |
| Used in environment KPIs | ✓ | ✓ | ✓ | – |

## Implementation

| Strategy | Function in `backend/aggregators.py` |
|---|---|
| `afap` | `simulate_uncontrolled_profiles_from_sessions(chargers, charging_sessions, start_date)` |
| `alap` | `simulate_delayed_profiles_from_sessions(chargers, charging_sessions, start_date)` |
| `avg` | `simulate_avg_charging_profiles_from_sessions(chargers, charging_sessions, start_date)` |
| `ocost` | `simulate_cost_optimal_operation(chargers, charging_sessions, start_date)` |

All four take a `{charging_point_id: rated_power_kW}` dictionary, an iterable of
`(cp_id, start, end, consumption_kWh)` rows and the first day of the window as `YYYY-MM-DD`, and
return `(load, up_flex, down_flex)` as lists of 288 floats. The local simulators use Polars for the
vectorised updates.

Modelling simplifications are collected in {doc}`../reference/known-limitations`.
